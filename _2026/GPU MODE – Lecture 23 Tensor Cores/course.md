So, what does CUTLASS 3 actually do with CuTe? Well, CUTLASS 3, as I said, is a superset of CuTe, and what we have done with it is to formalize a conceptual hierarchy of linear algebra components, in a way that decomposes the moving parts into orthogonal axes. Starting at the bottommost layer, we have the atom, what we call the atom layer.

which corresponds to the architecture instructions that are fundamentally supported by the hardware, and the associated metadata that we describe as a CuTe layout. This is the smallest set of threads and data that must participate to validly execute an architecture operation for math, copy, or whatever it may be.

On top of this, we build the tiled MMA and copy layer, which we like to call the spatial microkernel layer. The microkernel terminology here is kind of analogous to the CPU BLAS library, if you're familiar with it; if not, the spatial microkernel's responsibility is to take care of and abstract the complete spatial tiling of math and copy operations, where spatial refers to both threads and data.

And any permutations of those that we may wish to use. Basically, this layer allows us to write canonical loops for architecture-specific operations, regardless of how wildly complex the instruction layouts are. That means we can do a single for loop for copies and triple nested for loops for GEMMs. I'll show an example of that later.

For the asynchrony, this fundamentally addresses the first problem that I demonstrated—that of interleaving instructions and validating these layouts and index bookkeeping. The second layer here, the temporal microkernel, describes the complete temporal tiling of multiple spatial microkernels that compute one output tile. You can view this as an orchestration of multiple TMA MMAs and copies.

They make use of architecture-specific synchronization, warp specialization, and software pipelining to set up the proper instruction interleaving that you need to hide latencies from global memory, manage asynchrony, etc. So this is abstracting and letting you reason about the asynchrony, as well as the shared memory management.

On top of this sits the kernel layer, which consists of the outer loops that invoke the collectives and do things like load balancing across different output tiles, thread marshaling into their specialized regions, grid planning—which is deciding how many thread blocks to launch, how many clusters to set up, etc.

As well as constructing the arguments coming from the host side and then mapping them onto the ABI when the kernel actually launches. The device layer in CUTLASS is kind of just a shim.
